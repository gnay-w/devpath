# 0108 map 语义

## 目标

能说明并发写 map 的后果与读缺键的两种写法；对应 curriculum 验收。

## 写本篇时的基础假设

- 0102 已会：nil map 可读/`len`、不可写；零值可用。  
- 缺口：缺键零值 vs 逗号 ok；并发写后果。

## 正文

### 一句话

`map` 像 Java `HashMap`：**缺键给值类型零值**（不是一律 `nil`）；要区分「没有」用 **逗号 ok**；**不是线程安全**——并发写/读写常直接 fatal，不是安静算错。

### 缺键：零值 vs 逗号 ok

```go
m := map[string]int{"a": 1}
fmt.Println(m["b"]) // 0  ← int 零值，不是 nil、也不 panic

v, ok := m["b"]
// ok == false → 键不存在；v 仍是零值
```

值类型决定「缺键长什么样」：`int`→`0`，`string`→`""`，`*T`→`nil`。

**坑：** 真实值也可能是零值时，单靠 `m[k]` 分不清「没有」和「有且为零」。

| 写法 | 适用 |
|------|------|
| `v := m[k]` | 零值当「没有」也行（如计数器缺了就当 0） |
| `v, ok := m[k]` | 必须区分「没有」和「零值」 |

已存在且值为 0：`v, ok := m["a"]` → `0, true`。

### 并发：为何会 fatal？

map 内部是哈希表（桶、溢出链、可能扩容重哈希）。多 goroutine 同时改这些结构会**破坏内部不变量**——比「偶尔算错」更糟（错误结果、甚至死循环）。

Go 选择 **fail-fast**：运行时检测到并发写/读写 → `fatal error: concurrent map writes`（或 `concurrent map read and map write`），**进程直接挂**。这不是普通 `panic`，`recover` **救不回来**。

和 Java 普通 `HashMap` **像**（都非线程安全）；差异是 Go 更常当场崩，而不是 silently 坏数据。

要并发：外面加 `sync.Mutex`，或确认场景后再用 `sync.Map`（细节 → 0212）。

### 边角

| 点 | 记住 |
|----|------|
| `delete(m, k)` | 删不存在的键 → no-op |
| `range m` | 顺序不定，别依赖插入序 |

### 对照 Java

| Java | Go |
|------|-----|
| `get` 缺键 → `null`（引用） | 缺键 → **值类型零值** |
| `containsKey` / `getOrDefault` | `v, ok := m[k]` |
| 普通 `HashMap` 非线程安全 | map 同样；并发常 fatal |
| `ConcurrentHashMap` | `Mutex` 包一层，或 `sync.Map` |
